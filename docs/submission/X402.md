# x402 room top-up (testnet)

A local agent can top up a Fork Night room with **5 test credits** by paying **1.00 test USDC** through [x402](https://github.com/x402-foundation/x402), on **Solana devnet** or **Base Sepolia**. The route answers an unpaid request with an HTTP 402 offer, verifies the agent's signed payment, records a durable intent, settles it through the public `x402.org` facilitator, and only then credits the room through the pilot's existing refill. The image worker, the dollar ceiling and `/pilot` are unchanged.

What this proves: **x402 on Solana devnet and Base Sepolia gated a room top-up of test credits; continuations then run on the operator's approved allowance.** Testnet USDC is free from Circle's faucet, so a payment proves the payment rail, not real backing. Room credits are one pooled count, so a receipt explains a credit change, not a particular image. Test USDC never pays for image generation and never raises the operator's dollar ceiling. No mainnet funds moved.

## How it works

`POST /api/x402/fund/[fundingRef]` is an App Router route on the Node runtime. `fundingRef` is an opaque random token that local configuration maps to a room. Room and guest identifiers never reach the facilitator or a chain: the payment forwarded for verification and settlement names only the generic funding endpoint, and the Solana memo is a random offer reference.

1. **Offer.** Without a `PAYMENT-SIGNATURE` header, an eligible room gets HTTP 402 with a `PAYMENT-REQUIRED` header: x402 v2 `exact`, 1.00 test USDC, on Solana devnet (with a fresh seller memo) and Base Sepolia (EIP-3009), with a 120-second window. A room that is closed, not opted in or at its steward's top-up ceiling gets 409 and no offer, so an agent never pays a room that would refuse it.
2. **Match and verify.** The route decodes the payment, rebuilds the exact requirement (including the echoed Solana memo), checks the payment against it, and asks the facilitator to verify it. On Solana it also decodes the transaction: exactly one memo equal to the offer's and exactly one transfer of 1.00 USDC to the room's receiving account. On Base Sepolia it accepts only an EIP-3009 authorization to the receiving address within the offered window.
3. **Durable intent.** Before anything settles, a write-once intent is stored in the pilot's private receipts bucket. It is keyed by the payment authorization itself: the EIP-3009 payer and nonce, or the Solana memo. If the intent cannot be written, nothing settles.
4. **Settle, then credit.** The route settles explicitly and credits only a confirmed success, through the existing `pilot_refill_room` with request ID `UUIDv5(network:transaction)`. Repeating the same payment, or reconciling it later, therefore adds nothing. A receipt with the transaction link is stored next to the intent.
5. **Anything uncertain waits for the chain.** A pending or ambiguous settlement returns 202 and keeps the intent. `npm run x402:reconcile` checks the chain: the EIP-3009 authorization state and its `AuthorizationUsed` event on Base Sepolia, or the memo-tagged transfer on Solana devnet. It credits only a proven payment, and marks a payment expired only once it can no longer settle.

Each top-up uses the same refill as the local operator control: 5 room credits, 5 more guest attempts and request headroom, with the dollar ceiling unchanged. The same top-up can also be paid through MPP on Tempo Moderato testnet, with its own per-room limit; see [MPP room top-up](MPP.md).

## Run it locally

The route exists only on a loopback development server with `PILOT_LOCAL_CONTROLS=1`, a local funding configuration and a local agent token, which setup creates and the agent payer sends. It returns 404 everywhere else, including any hosted deployment, and the x402 code is not loaded until those checks pass. Use throwaway testnet wallets only.

```sh
# 1. Create throwaway wallets and the local agent token (if missing), and opt one room in under a random funding link.
npm run x402:setup -- init --room <roomId> --steward <guest profile UUID> --max-top-ups 2
# 2. Fund the two payer addresses and the Solana receiving address at https://faucet.circle.com, then:
npm run x402:setup -- check
# 3. With the local app running on port 3005 (PILOT_LOCAL_CONTROLS=1), let the agent pay:
npm run x402:fund -- --network solana --room <roomId>
npm run x402:fund -- --network base --room <roomId>
# 4. Evidence, and recovery for anything pending:
npm run x402:status
npm run x402:reconcile            # dry run; add -- --apply to write
```

Run the app from this checkout, so the route and the agent read the same `.local/x402` token and configuration; `--room` is required when several rooms are opted in. The agent payer signs at most one payment per run and saves it under `.local/x402/payments/` before sending. If an answer is lost, `--resume <record>` re-sends that same signed payment; it never signs a new one. A pending payment is resolved by `npm run x402:reconcile`, which tells the operator when signing a new payment is safe.

## Not included

Payments from browser wallets, a treasury paying the route directly (a Squads vault through `spending_limit_use` with a custom client, or a Safe as the x402 payer), pay-on-delivery per image, `upto` or batch sessions, buying inference from x402 suppliers, and mainnet settlement are later work. Each needs its own decisions about real funds, refunds and accounting. Treasury-funded payer wallets have already paid on testnet; see [Treasury hops](TREASURY-HOPS.md).
